## What this project is

The Emacs Package Developer's Handbook — a single-document guide to Emacs package development, maintained as `README.org` and published as HTML at https://alphapapa.github.io/emacs-package-dev-handbook/.

**Current mission:** update the handbook (last substantively updated ~2024, roughly Emacs 28/29 era) to target **Emacs 31**. Goals in approximate priority order:

1. Remove or rewrite references to deprecated functions.
2. Remove tips/tricks/advice that are no longer true or needed.
3. Add sections for package-development-relevant features added in Emacs 28/29/30/31.
4. Add an overview of changes to the development landscape since the last version.
5. Topic by topic, update recommended packages — add new ones, remove unmaintained ones (careful: packages with no commits for years may still work perfectly fine).
6. Update benchmarks of code snippets.
7. Prune links to dead websites.

## Source of truth and generated files

`README.org` (~5000 lines) is the **only** hand-edited content file. Everything else is generated from it via file-local save hooks (see the `Local Variables` block at the end of `README.org`):

- `index.html` — Org HTML export of README.org (renamed from README.html). **Never edit by hand.**
- `epdh.el` — tangled from the src blocks in README.org marked `:tangle epdh.el`. **Never edit directly**; edit the corresponding src block in README.org instead.
- Table of contents (`:CONTENTS:` drawers) — regenerated by `org-make-toc` on save; don't edit ToC drawers by hand.

The full regeneration pipeline only runs when README.org is saved inside Emacs with the file-local hooks active (they require `org-make-toc` and alphapapa's `unpackaged/org-export-html-with-useful-ids-mode` for stable heading IDs). Content edits made outside Emacs are fine, but regenerating `index.html`/`epdh.el` afterward requires an Emacs session. Use `emacsclient` (never bare `emacs`) for any elisp evaluation, tangling, or export.

## README.org structure and conventions

- Top-level sections: `Emacs Lisp` (the bulk, topics in alphabetical order), `Blogs`, `People`, `Contributions`, `Tasks`, plus a `COMMENT Code` section holding maintenance tooling.
- Each topic under `Emacs Lisp` uses recurring subheading names: `Articles`, `Best practices`, `Examples`, `Libraries`, `Tools`, `Snippets` — keep new content in that scheme and in alphabetical order.
- Headings carry filter tags (`:libraries:`, `:built_in:`, `:alists:`, etc.) and stable `CUSTOM_ID` properties used for HTML anchors — preserve existing `CUSTOM_ID`s so published links don't break.
- Many entries are just an org link as the heading itself; prose, when present, goes in the body.
- Benchmark results are Org tables produced by evaluating src blocks that call the `bench`, `bench-multi`, `bench-multi-lexical`, `bench-dynamic-vs-lexical-binding`, and `bench-multi-lets` macros (defined in src blocks tangled to `epdh.el`; `epdh.el` requires `dash`, `s`, and `map`). To refresh a benchmark, re-execute its src block in Emacs with `epdh.el` loaded and replace the `#+RESULTS:` table.

## Branch model

This repo is a fork of `alphapapa/emacs-package-dev-handbook` (remote `upstream`).

- `master` — pristine mirror of `upstream/master`. Never commit work here; only fast-forward from upstream.
- `develop` — integration trunk and default branch. All revision work lands here. See `PLAN.org` for the phase roadmap and the acceptance checklist that gates phase-sized merges.
- Feature branches — branch from `develop`, merge back into `develop`.

## Conventions

- Commit messages follow a `Prefix: description` style, e.g. `Add: Eask`, `Change: Remove image`, `Meta: Add .gitignore`, `Update HTML`.
- There is no build system, linter, or test suite; "building" is the Org save-hook pipeline described above.
